## الثوابت التي لا يجوز أن تُفقد مقابل السرعة

1. الاختبارات لا تُحذف ولا تُضعف لإظهار انخفاض الزمن: نزاهة الموارد/النقد والعهدة، حالات الرفض والخصوم، مطابقة Replay/SQLite، توافق الحفظ القديم، استقلال NPC، وقواعد `default-off` تبقى بوابات.
2. **إغلاق أي مرحلة برمجية أو تغيير Schema/Rules** يتطلب full regression على **SHA النهائي** في Python 3.10 و3.13، والفحوص الموجّهة/التحمّل المطلوبة لنطاقها. الاستثناءات يجب أن تكون **توثيقية بحتة ومثبتة**؛ لا تُعاد تسمية تغيير كود كي يتجاوز البوابة.
3. بوابات GitHub المطلوبة لا تتحول إلى حالات `skipped` أو `pending` صامتة بسبب `paths`. افحص سياسة Required Status Checks قبل تغيير workflow أو دمجه.
4. التفريق بين ثلاث نتائج: `FAST_FEEDBACK_PASS`، و`FULL_EXACT_SHA_PASS`، و`RELEASE_GATE_PASS`؛ الأولى لا تعادل الأخيرة. أي فشل في الوظائف الإلزامية يمنع ترقية/إغلاق المرشح.
5. لا تعدّل `main`؛ لا تُوقف أو تحذف workflows تاريخية مطلوبة من فروع أخرى قبل حصر تبعياتها؛ ولا تجعل pull_request من مصدر غير موثوق قادرًا على قراءة أسرار أو تشغيل أوامر بامتيازات كتابة.

## شكل بوابات CI المقترح

- **Docs-only:** حارس يقرأ قائمة الملفات المتغيرة من GitHub ويصنفها بسياسة مثبتة؛ لا تشغيل اختبار محرك طويل ما لم يتغير `simulation/src/**` أو `simulation/tests/**` أو `simulation/scenarios/**` أو ملفات workflow/تثبيت الاختبارات/عقد إصدار أو manifest مؤثر. لا تكفي `paths-ignore` وحدها لو كان الفحص مطلوبًا في حماية الفرع؛ حافظ على check نهائي ناجح/راسب صريح مع jobs مشروطة.
- **Smoke:** compile + مجموعة قبول خصومية صغيرة + Version invariants / replay + تحقق من schema/rules؛ **هدف أولي** بضع دقائق وليس وعدًا حتى تُقاس النتائج.
- **Targeted:** اختبارات الجزء المعدّل في كلا الإصدارين، تشمل الحالات العدائية، الاختلافات الواقعية، وبعض قواعد حفظ/اقتصاد؛ لا تستخدم وحدها لإغلاق إصدار.
- **Full release:** `python -m pytest -q` مع خطوات التوافق القديمة و`PLAY-47` endurance إن كان نطاق الإصدار يعتمد عليها، على SHA الحقيقي ورؤوس الفروع المؤكدة، ثم قرار الترقي/الإغلاق.
- **Scheduled/manual endurance:** يجوز إعادة الاستخدام عند اختبار الأداء ومراقبة الانحدارات بعد الثبوت، **لكن لا تؤجّل اختبار Endurance المطلوب لإغلاق مرحلة إلى ما بعد اعتمادها**. أي تقرير يومي لا يغني عن بوابة SHA النهائية.
- **Concurrency:** ضوابط `cancel-in-progress` الموجودة لا تُعطّل عمدًا؛ لا يُلغى تشغيل نهائي معتمد بسبب Push جديد دون توثيق إلغاء صلاحية المرشح السابق.

## أوامر قياس مبدئية، لا نتائج منفّذة

داخل `simulation/`، وعلى checkout ثابت قبل التعديل وبعده:

```bash
PYTHONPATH=src python -m pytest -q --durations=30
PYTHONPATH=src python -m pytest -q -s scenarios/test_village/test_play47_closure_endurance.py
python -m cProfile -o /tmp/carlos-perf.pstats -m pytest -q scenarios/test_village/test_play47_economic_audit.py
```

استخدم سجلات `GitHub Actions` للتوقيت ومخرجات `pstats` بعيدًا عن ملفات المحرك؛ لا تعتمد `cProfile` للحكم على زمن التشغيل النهائي لأنه يضيف كلفة. ضع baseline ماديًا لكل Python، لنفس حجم العالم وعدد الأحداث؛ أرفق المصدر/الـSHA ووقت التشغيل وعدادات Replay وعدد الأحداث.

## قرارات المخاطرة والأهداف

- **أولوية قريبة:** CI-00 ثم CI-01، مع CI-03 مستقلة. هذا يعطي Feedback سريعًا قبل أخطار تعديل `WorldState`. لا يبدأ CI-04 قبل ظهور دليل واضح من CI-03.
- **أهداف مقارنة لا وعود:** خفض الزمن الكلي للـfeedback البسيط بقدر كبير، ثم استهداف خفض زمن `audit/endurance` دون تقليل سيناريوهاتها؛ عرّف معيار نجاح كمي بعد قياس baseline والعينات. لا تعد بتحقيق وقت ثابت في Runner سحابي متغير.
- **تراجع آمن:** أبقِ الأصل Workflow قابلًا للاستعادة والـSHA المرجعي وأسماء check اللازمة، وأوقف التحسين إن تغير canonical digest أو Replay أو audit أو سلوك رفض الملفات القديمة.
- **التوافق مع PLAY-48:** التحسينات هنا عمل بنية مستقل؛ لا تُحدث تغيير Schema/Rules أو قواعد NPC من أجل جعل CI أخضر. متابعة مراحل اللعب خاضعة لبواباتها الخاصة.
- **التحقق الخارجي:** لا تعتبر هذه الخطة أو نجاح GitHub Actions اعتمادًا لنسخ طويلة الأمد أو اختبارات Windows أو مراجعة مستقلة. تبقى P0 مفتوحة.

**تعريف النهاية:** لا تسمَّ `CI_OPTIMIZED` حتى توجد مقارنة A/B قابلة للإعادة مع نتائج اختبار متساوية وخطة تراجع موثقة. **لم تُعدّل workflows أو خوارزمية الأداء بهذا المستند.**
