## المشكلة المثبتة والقياس

`PlayerGateway._state()` يقرأ عبر `SQLiteEventStore.load()`. الصفحة العربية تنشئ سبعة إسقاطات مستقلة، وكل إسقاط يعيد قراءة/إسقاط الحالة. `needs` و`conversations` يستدعيان `store.verify()` أيضًا، وكل تحقق يعيد التشغيل من السجل ثم يقارن snapshot. `player_handoff()` يستدعي 11 إسقاطًا؛ خمسة منها تتحقق من السجل بشكل مستقل.

استخدمت `bench_replay_store.py` نفسه على رأس الأساس النظيف، Python 3.12.14، مع قاعدة مؤقتة. عند 100 حدث كان replay الكامل 2 `SELECT` و23.857 ms وسيطًا؛ لا توجد مشكلة N+1 في SQL منذ 01-O.

| القراءة / قاعدة 172 حدثًا | بلا snapshot | مع أحدث snapshot |
|---|---:|---:|
| رسم الصفحة: استدعاءات replay في الطلب | 11 | 11 (تتضمن إعادة تشغيلين كاملتين للتحقق) |
| رسم الصفحة: SELECT | 33 | 33 |
| رسم الصفحة: زمن وسيط | 687.844 ms | 135.863 ms |
| تسليم اللاعب: استدعاءات replay في الطلب | 21 | 21 (تتضمن خمس إعادات كاملة للتحقق) |
| تسليم اللاعب: SELECT | 63 | 63 |
| تسليم اللاعب: زمن وسيط | 1239.831 ms | 314.870 ms |

مخرجات الصفحة بقيت 11,540 بايتًا، ومخرجات التسليم 1,637 بايتًا. الأرقام وصفية لبيئة Python 3.12 هذه، وليست حدود أداء محمولة. قاعدة المتصفح المؤقتة لا تنشئ snapshot أثناء اللعب، لذا القراءة المعتادة تميل إلى عمود «بلا snapshot».

أعيد إنتاج تعارض قراءة حتمي: بعد أن يقرأ `load()` صف رأس العالم، أُدخل كاتب SQLite حدث `TimeAdvanced` صحيحًا قبل استعلام snapshot/suffix. القارئ أخفق بـ`IntegrityError: world head mismatch` رغم أن `verify()` بعده أكد رأس الكاتب revision 1. السبب أن استعلامات `load()` المستقلة لا تشترك في معاملة قراءة واحدة.

## الملفات والعقود المقترحة

- `src/carlos_sim/store.py`: معاملة قراءة SQLite قصيرة تجعل قراءة رأس العالم وsnapshot وسجل الأحداث ذرية؛ نطاق قراءة متسق يعيد إسقاطًا موثقًا واحدًا لبقية إسقاطات الطلب. يظل `verify()` يقارن إعادة البناء الكامل بـsnapshot. لا bypass للتحقق ولا تخزين بعد نهاية النطاق.
- `src/carlos_sim/player_gateway.py`: استعمال إسقاط القراءة نفسه خلال طلبات القراءة المركبة، مع بقاء نتائج كل أمر player-scoped ومفصولة عن `WorldState`.
- `src/carlos_sim/player_handoff.py` و`scenarios/test_village/play_village_web02_ui.py`: تجميع عرض الذاكرة/الحالة/الموقع والصفحة على مراجعة واحدة. لا تغيير في HTML أو قواعد اللعب.
- `src/carlos_sim/player_perception.py`, `player_sustenance.py`, `player_eating.py`, `player_gift_history.py`, `player_conversations.py`: حصر استعلامات الأحداث عند `seq <= state.revision` كي لا يدخل حدث أحدث من الإسقاط في نتيجة تاريخية.
- اختبارات: `tests/test_replay_join.py`، `tests/test_player_needs_gateway.py`، `tests/test_playable_web03.py` واختبارات جديدة مركزة لنطاق القراءة المتسق والذاكرة.
- القياس: `scenarios/test_village/bench_replay_store.py` أساس replay؛ أضيف قياس وصفي لرسم الصفحة وتسليم اللاعب عند أحجام ووجود/غياب snapshot. لا threshold زمني متعلق بالعتاد.

### عقد النطاق

1. بداية طلب القراءة تفتح SQLite read transaction وتتحقق من حالة واحدة باستخدام السجل وsnapshot.
2. كل إسقاط داخل النطاق يحمل `world_id/time/revision` نفسها. انتهاء النطاق يغلق المعاملة ويلغي أي cache مؤقت؛ القراءة التالية ترى الكاتب الذي اكتمل.
3. لا يسمح النطاق بأي append أو snapshot، ولا يعود `WorldState` الخام للواجهة/المستخدم.
4. كل تاريخ أحداث يقرأ فقط حتى مراجعة الحالة التي بُني منها؛ الترتيب والحدود والخصوصية الحالية تبقى كما هي.
5. لا يضيف GET/التسليم أي حدث أو أمر، ولا يغير استجابة القراءة المفردة أو سجل الأحداث أو hashes.

## معايير القبول

- مخرجات `PlayerGateway` المفردة والصفحة والتسليم قبل/بعد التحسين متطابقة للحالة المجمدة نفسها، بما فيها `details`, ترتيب الذاكرة، الحدود، `time` و`revision`.
- في سيناريو 172 حدثًا، لا تتجاوز الصفحة عمليتي replay (واحدة كاملة ومقارنة snapshot) و8 استعلامات `SELECT`؛ ولا يتجاوز التسليم العمليتين و11 استعلامًا. يقاس الزمن ويُبلّغ عنه دون عتبة عتادية.
- اختبار كاتب منفصل يتداخل بين قراءة الرأس والسجل: القراءة تعيد حالة متماسكة، ثم يرى الطلب التالي المراجعة الأحدث. لا خطأ integrity زائف ولا نتيجة مركبة من مراجعات مختلفة.
- عملية كتابة فعلية أثناء نطاق القراءة لا تتسرب إلى memory/history أقدم من مراجعتها؛ بعد إغلاق النطاق تصبح مرئية في القراءة التالية.
- النطاق للقراءة فقط: عدد الأحداث/الأوامر ثابت، و`verify()` بعده يساوي الحالة السابقة؛ لا تسريب لمخزون/NPC knowledge أو `WorldState`.
- snapshot/full replay/reopen، الحدث المفقود ورفض الإصدار غير المدعوم تبقى كما هي؛ الانحدار الكامل على Python 3.10 و3.13 مطلوب للإغلاق.

## حالات الفشل والمخاطر

- قد ينتظر الكاتب حتى ينتهي طلب القراءة لأن معاملة القراءة تحجز نسخة SQLite ثابتة؛ يجب إبقاء النطاق قصيرًا وعدم تضمين محاكاة أو IO خارجي داخله.
- تقليل `verify()` دون إثبات حالة واحدة يضعف مصدر الحقيقة؛ لذلك النطاق يبدأ بتحقق واحد كامل ولا يستمر بعد نهاية الطلب.
- استعلامات JSON التاريخية قد تبقى O(عدد الأحداث)؛ لن أضيف فهرسًا أو جدول إسقاط دائم إلى هذا النطاق. نقيسها كحد متبقٍ منفصل إذا استمرت بعد إزالة replay المكرر.

## التنفيذ ونتائج القبول

نُفذت المهمة على `feature/carlos-read01-20261126` انطلاقًا من رأس NEEDS-01 أعلاه، في نسخة عمل منفصلة. كود التنفيذ والاختبارات عند commit `f4c795784b9f80a87ddd68794ca88bb3565168fc`. بقيت تغييرات الفرع السابق دون لمس. التنفيذ محصور في `store.py`, تاريخ أحداث اللاعب، تجميع الصفحة وتسليم اللاعب، والاختبارات؛ لا تعديل Schema/Rules أو HTML أو أحداث اللعبة.

- `SQLiteEventStore.load()` و`verify()` يستخدمان معاملة قراءة ذرية. تحقّق `verify()` مرة واحدة داخل النطاق؛ الحالة لا يعاد استخدامها خارجه. في غياب snapshot تكفي إعادة البناء الكامل بدل تكرارها مرة ثانية.
- `read_consistent(world_id)` يثبت مراجعة موثقة لمدة طلب الصفحة أو handoff ويمنع append/snapshot داخلها. كل قراءات تاريخ اللاعب المحددة تقيد استعلام SQL بـ`seq <= state.revision`.
- اختبار SQLite باتصالين يثبت أن كاتبًا يتداخل بعد SELECT الرأس لا يسبب فسادًا زائفًا، وأن القراءة التالية ترى المراجعة الجديدة. اختبار history يثبت أن هدية ملتزمة بعد التحقق لا تدخل إسقاط المراجعة الأقدم. اختبار النطاق يثبت إعادة الاستخدام المؤقت، منع الكتابة، وانتهاء cache عند الخروج.
