## ما تنفذه الأدوات والاختبارات الموجودة

- `src/carlos_sim/backup.py` ينشئ حزمة مستقلة بواسطة SQLite backup API، ويفحص كل العوالم عبر `integrity_check` وreplay، ويرفض تعديل هدف موجود. `verify_backup_bundle` يفحص نسخة مؤقتة؛ `restore_backup_bundle` لا ينشر هدفًا قبل التحقق منه.
- `src/carlos_sim/resumable_play.py` يحصر الفتح والاستئناف على `disposable_test=True`، ويجري فحصًا للقراءة فقط للإصدار والملف قبل فتح الجلسة. إغلاق الجلسة لا يقدم الزمن.
- `tests/test_backup_resume.py` يغطي WAL، نسخة ثابتة أثناء استمرار الأصل، استعادة رحلة معلقة، فساد الحزمة/manifest، إصدار غير مدعوم، عدم الكتابة فوق هدف، وفشل النسخ.
- `tests/test_player_needs.py::test_snapshot_resume_keeps_partial_rest_and_frozen_time` يغطي snapshot وإعادة فتح ملف SQLite أثناء راحة جزئية، لكنه لا يستعيد الحزمة المستقلة.
- `tests/test_play_living_resumable_batch_03.py` يغطي الاستمرار متعدد الشخصيات، الاستئناف أثناء السفر ورفض الإصدار القديم دون تعديل.
- PLAY-LOOP أضاف عملًا للاعب محفوظًا في سجل الإنتاج والموعد المجدول، لكن لا يوجد بعد اختبار يستعيد حزمة مستقلة أثناء العمل ويكمله دون تكرار المنتج أو الأجر.

## النطاق والمهام

1. **SAVE-01a — تحليل الفجوة والعقد:** أُنجز بهذا الملف قبل تنفيذ الاختبارين؛ إعادة استخدام `backup.py` و`ResumableTestSession` فقط.
2. **SAVE-01b — استعادة عمل لاعب جارٍ:** اختبار SQLite مؤقت يبدأ وصفة خبز فعلية، ينتظر جزءًا من مدتها، ينشئ حزمة، يغلق الجلسة، ثم يستعيد نسخة جديدة. يثبت تطابق الحالة والموعد والمخزون والأوامر بعد الفتح، تجميد الزمن عند الإغلاق، وعدم دفع الأجر/إضافة الناتج قبل due، ثم تسوية واحدة عنده.
3. **SAVE-01c — استعادة راحة جزئية:** اختبار عالم اختباري يثبت أن التعب والجوع والموعد المتبقي يبقون كما هم بعد استعادة حزمة، ولا تقع الراحة قبل due؛ عنده بالضبط ينطبق أثر الراحة المحدد. السفر المشفوع بحزمة فساد/توافق تغطيه الاختبارات الحالية، وتبقى حارسًا في الانحدار.
4. **SAVE-01d — فحص وتوثيق:** تشغيل الاختبارات الموجهة ثم الانحدار الكامل Python 3.10/3.13 على آخر كود/اختبارات، فحص الفرق، وتحديث WORK_QUEUE/ROADMAP/HANDOFF بنتائج SHA الفعلية وحدود P0.

## معايير القبول

- الحزمة المستعادة تطابق الحالة الملتقطة دلاليًا وبالـreplay، بما يشمل `production_jobs` و`scheduled` وموعد العمل/الراحة، مراجعة SQLite وسجل الأوامر.
- عند فتح جلسة لا يتقدم الزمن تلقائيًا. خلال الإغلاق لا يتغير وقت العالم أو السجل.
- لا يظهر ناتج الخباز أو الأجر قبل الموعد؛ عند due يظهر كل منهما مرة واحدة من مدخلات وأرصدة البداية الفعلية، ويبقى مجموع النحاس ثابتًا.
- الراحة الجزئية لا تطبق استرداد التعب مبكرًا أو مضاعفًا؛ الأكل/الجوع والزمن يواصلان قواعدهما المسجلة.
- تلف الحزمة، manifest متلاعب، هدف موجود، أو قواعد حفظ غير مدعومة تظل حالات رفض آمن دون ترحيل أو كتابة على المصدر/الهدف. يعاد تشغيل اختبارات الرفض الحالية ضمن المجموعة الموجهة.
- لا تغيير في Schema/Rules أو أحداث الإنتاج/الراحة، ولا CLI/واجهة/قصة أو `main`. العمل على SQLite مؤقت في `tmp_path`، مع `disposable_test=True`.

## المخاطر والحدود

- نجاح هذه الاختبارات يثبت استمرارًا واستعادة **تقنيين داخل بيئة الاختبار**، ولا يثبت تحمل انقطاع الطاقة أو صلاحيات Windows أو نسخًا خارج الجهاز أو RPO/RTO؛ بوابة `P0_PRODUCTION_NOT_APPROVED` والمراجعة المستقلة تظلان مفتوحتين.
- manifest وSHA يثبتان تطابقًا بعد الالتقاط فقط، ولا يمنعان مشغلًا بصلاحية محلية من تعديل الملف والحزمة معًا.
- إذا كشف الاختبار نقصًا في سجل الأحداث أو موعدًا لا يعاد بناؤه، يُصلح السبب المحدد فقط ثم يعاد الاختباران والانحدار؛ لا ترقية تلقائية للحفظ ولا إعادة توليد عالم قديم.
