# بروتوكول التطوير والمراجعة — محرك كارلوس

**مُكمل إلزامي تنظيميًا** للخارطة: [ROADMAP.md](ROADMAP.md).  
هذه الوثيقة إجرائية؛ لا تغير قواعد المحرك أو حالة العالم بمجرد اعتمادها.

## A. قبل كتابة أي كود

1. اقرأ README وتقارير المرحلتين السابقتين، وثيقة المعمارية وقرارات التصميم.
2. تحقق من الفرع وHEAD الحاليين ونجاح آخر CI؛ لا تفترض أن آخر رسالة في المحادثة هي أحدث commit.
3. حدد الهدف السلوكي بدقة وحدد ما لن يُنفّذ في هذه المرحلة.
4. سجل نوع التغيير: **behavior** أو **event/schema** أو **persistence** أو **security/privacy** أو **performance** أو **integration**.
5. اكتب قائمة الأحداث والعقود والمدخلات والصلاحيات والتوقعات وحدود المعرفة ومصادر الموارد.
6. حدد استراتيجيات الفشل وما الذي يحدث لو توقف التنفيذ في منتصف الأمر.
7. حدد ما إذا كانت المرحلة تحتاج تعديل Schema / Rules / migration، وما إذا كانت تتطلب flag.
8. اختَر عالم اختبار من 5–10 شخصيات عادة؛ لا تبدأ باختبارات ضخمة دون سبب.

## B. قالب بطاقة المرحلة

- **المرحلة:** ID — اسم واضح.
- **الفرع / HEAD / baseline:** قيمة مؤكدة، مع branch base.
- **المشكلة:** فجوة فعلية، مع مثال يمكن إعادة إنتاجه.
- **الهدف:** ناتج يمكن قياسه أو ملاحظته.
- **الموجود حاليًا:** أي مكونات يمكن إعادة استخدامها.
- **حدود التنفيذ:** ما ضمنها وما خارجها.
- **عقود الأحداث:** event types, payload, capability, timestamp, actor_id, source of truth.
- **المعرفة والخصوصية:** ما يحق لكل فاعل معرفته وكيف وصل إليه.
- **الأثر على Schema/Rules:** ثابت أو تغير مع سبب وخطة استعادة.
- **الخطر الرئيسي:** واحد أو أكثر، وكيف يمنع الاختبار وقوعه.
- **الاختبارات:** وحدة / تكامل / سيناريو / replay / rollback / security.
- **المراجعة:** من أو ما منهج التحقق المستقل؛ قائمة المشاكل المكتشفة.
- **النتيجة:** أرقام ناجحة موثقة وروابط GitHub Actions وتقرير نهائي.
- **الخطوة التالية:** قرار واضح، لا إعلان اكتمال لنظام غير منفذ.

## C. قائمة فحوص أساسية لا تُحذف دون مبرر

- [ ] سلوك ناجح عندما توجد الموارد والوقت والقدرة والمعلومات.
- [ ] حدود 0 والكمية الناقصة والقيمة المجهولة: unknown != zero.
- [ ] رفض المصدر المزور أو الهوية المزورة أو الحدث غير المصرح.
- [ ] ترتيب صحيح لتزاحم شخصيتين على المورد أو الموعد نفسه.
- [ ] عدم مضاعفة الحدث أو إنجاز الفعل مرتين عند إعادة الطلب.
- [ ] إيقاف الجلسة يمنع تقدم الزمن والأفعال.
- [ ] فشل عنصر داخل command batch يلغي جميع آثار الأمر.
- [ ] حفظ snapshot وإعادة بناء من جميع الأحداث والتطابق الدلالي.
- [ ] إعادة فتح قاعدة البيانات والحفاظ على الحالة والأحداث.
- [ ] تطابق قواعد العالم السابقة عند تعطيل الميزة إن كانت opt-in.
- [ ] عدم وصول planner إلى معلومات بعيدة أو سرية غير مرخصة.
- [ ] بقاء تصرف كارلوس بيد اللاعب دون تحريك من النموذج.
- [ ] نسخة Python 3.10 و3.13 تمر بجميع اختبارات المشروع.
- [ ] مراجعة مستقلة تسبق الحكم بالاكتمال.
- [ ] CI يعكس **آخر commit** بعد التصحيح والتوثيق.

قد لا تنطبق بعض الفحوص على مرحلة وثائقية بحتة؛ اكتب **N/A مع السبب** ولا تعتبر عدم تشغيل الاختبارات نجاحًا مفترضًا.

## D. خطوات المراجعة المستقلة

1. اقرأ diff دون الاعتماد على وصف المنفّذ، مع تدقيق حدود الثقة.
2. جرّب مدخلات مزورة أو ناقصة: وقت غير صحيح، revision قديم، owner مجهول، مخزون ناقص، موقع بعيد، حدثان متنافسان.
3. تأكد أن كل event قابل للإعادة وأن snapshot لا يصبح مصدر حقيقة بديلًا عن السجل.
4. افحص إن كانت القرارات تعتمد على WorldState غير مسموح للشخصية معرفته.
5. تأكد من عدم إغفال التحقق في path سريع أو كاش أو service جديد.
6. راقب if/flags الجديدة في LivingWorldEngine: هل تغير ترتيب الأولويات في أوضاع قديمة؟
7. إن كان التحسين أداء: قارن نفس workload والقيم والحالة مع baseline، واذكر بيئة القياس وتباين النتائج. لا تتخذ التوقيت بوصفه برهان صحة.
8. كل ملاحظة تُصنّف: blocker أو regression أو improvement لاحق، مع اختبار يثبت الإصلاح.
9. أعد الاختبارات على آخر commit. المرحلة غير مغلقة طالما فحص مهم فاشل أو جارٍ ولم يُثبت نجاحه.

## E. إدارة الإصدارات والبيانات

- **Schema change:** إضافة/تغيير حقول حالة محفوظة أو أسلوب اشتقاقها أو صيغة snapshot. يلزم إصدار جديد عند كسر توافق البيانات.
- **Rules change:** أي اختلاف في التحقق/النتيجة/تفسير event قد يغير إعادة تشغيل البيانات القديمة؛ وثّق أثره وحاجة رفع رقم القواعد.
- **Test world:** يمكن إعادة إنشائه بقرار واضح؛ لا تفترض ذلك لقصة كارلوس الحقيقية أو عوالم قديمة مهمة.
- **Migration:** وثيقة انتقال تتضمن backup، فحص المصدر، التحويل، verify، rollback، واختبار عينات قبل أي overwrite.
- **Never silently migrate:** عند الشك ارفض فتح صيغة غير مدعومة بدل فرض قيم غير موجودة.

## F. سياسة الأداء

الاختبار السلوكي الافتراضي: **7 NPC تقريبًا**، ويمكن 5 أو 10 عند الحاجة. عند ربط عدة أنظمة 10–25؛ اختبارات 100–150 عند تعديل التزامن/المعمارية أو ظهور اختناق؛ آلاف الشخصيات بعد إثبات نضج المنطق. لا تُستبدل دقة السيناريو بأعداد كبيرة فارغة.

### متى نبدأ تحسينًا معماريًا؟

عندما يوجد أحد التالي: تراجع أداء واضح مقارنة بفرع سابق؛ زيادة غير متوقعة في عمليات SQL؛ حدود ذاكرة تمنع سيناريو مهم؛ تكرار إسقاط أو نسخ ذي أثر مثبت بالقياس. عندئذ نحدد baseline ونفصل الأداء عن السلوك في التقرير.

## G. الإغلاق والانتقال

لا تُسمى المرحلة «مكتملة» إلا إذا:
- توضح ماذا أضيف وماذا أُجّل.
- اجتازت الاختبارات ذات الصلة وأُعلن العدد الحقيقي وأرقام الأحداث منفصلة عنه.
- راجعها فاحص مستقل وأُغلقت الموانع وأُعيدت الاختبارات بعد آخر إصلاح.
- حُفظ التقرير والقرارات ورابط CI والـ HEAD.
- بقيت ملفات قصة كارلوس وmain دون تعديل إلا بطلب صريح.
- حُدّثت حالة المرحلة في ROADMAP.md من مخططة إلى مكتملة في نفس commit التوثيقي أو commit مستقل مثبت.

تدفق العمل: **تصميم → تنفيذ → اختبار → مراجعة → تصحيح → تحقق نهائي → توثيق → إغلاق**. لا تنشئ مراحل جديدة فقط لأن السابقة أنتجت كودًا؛ تحقق أولًا من قيمة السلوك الذي أضافته.

## H. بروتوكول تغيير خارطة الطريق (Living Roadmap)

هذا البروتوكول يُفعّل طلب المستخدم أن تكون خارطة كارلوس **قابلة للتعديل عند الحاجة**، لا خطة نهائية مغلقة.

- إذا كشف اختبار أو فحص أو تجربة لاعب تبعية أو مشكلة تصميم، قيّم تعديل الخارطة **قبل** إضافة ترقيع غير مدروس.
- سجّل القرار في [ROADMAP_CHANGELOG.md](ROADMAP_CHANGELOG.md): الدافع، الدليل، البدائل، التغيير، أثر التبعيات/الإصدارات، وحالة التنفيذ.
- راجع ROADMAP.md ثم ملف قرارات التصميم. لا تغيّر تقارير المراحل السابقة لإخفاء فجوة.
- أبلغ المستخدم بما تغير ولماذا؛ لا تُسوّق خطة وثائقية على أنها ميزة منفّذة.
- التغييرات المدمرة في حفظ العالم، ملفات قصة كارلوس أو main تتطلب موافقة صريحة.

## I. الحفظ والترحيل — بوابة P0 عابرة للمراحل

اقرأ [SAVE_COMPATIBILITY_POLICY.md](SAVE_COMPATIBILITY_POLICY.md) عند بدء **كل مرحلة**، وأجب في التقرير:
1. هل العالم المستخدم disposable أم محفوظ مهم؟ ما إصدار Schema/Rules الحالي والمستهدف؟
2. هل يغيّر الكود صيغة العالم أو دلالة replay أو أحداثًا قديمة؟ وما رد الفعل على الإصدارات غير المدعومة؟
3. هل يُحتاج إلى backup متسق، ومعاينة ترحيل على نسخة، وتمرين استعادة قبل تنفيذ التغيير؟
4. هل يوجد دليل `PRAGMA integrity_check` و`SQLiteEventStore.verify()` بعد استرجاع النسخة؟
5. هل ستُكشف خدمة محلية أو عامة؟ أعلام `bootstrap` و`*_authorized` ليست AuthN/AuthZ؛ لا تُعرض للعميل.

**P0 غير مُنفذة بعد.** قبل أول عالم طويل الأمد: اختبر أداة backup/restore وفحص سلامة وتوافق version على نسخة معزولة، وثق الفشل الآمن والاستعادة، واحصل على مراجعة مستقلة. لا تخلط وجود snapshots داخل نفس DB مع وجود backup.
